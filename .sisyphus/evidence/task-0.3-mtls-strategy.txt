================================================================================
DECISION: Self-Signed Certificates with Auto-Rotation (Per-Client mTLS)
================================================================================

STRATEGY COMPONENTS:

1. Certificate Source:
   - Self-signed Certificate Authority (CA)
   - CA generated once during initial setup
   - Server and client certificates signed by CA
   - RSA 4096-bit for compatibility
   - No external PKI dependencies

2. Rotation Strategy:
   - Automatic rotation every 90 days
   - Rotation trigger: Certificate age > 75 days OR startup if expired
   - Grace period: 15 days before expiration
   - Validation on every connection
   - Graceful restart (SIGHUP) for config reload

3. Scope:
   - Per-client certificates (individual isolation)
   - One server certificate (Go Bridge)
   - One client certificate (Rust Vault)
   - Future: Support multiple independent vault instances

4. Architecture:
   - Transport: gRPC over Unix Domain Socket (UDS) with TLS layer
   - Dual-layer security: mTLS (transport) + ephemeral tokens (application)
   - Defense in depth: Both layers must pass
   - Zero external dependencies: Self-signed CA

================================================================================
RATIONALE
================================================================================

WHY SELF-SIGNED CERTIFICATES?

✓ Zero external dependencies - works offline, no CA fees
✓ Operational simplicity - no third-party PKI management
✓ Fast deployment - no certificate signing delays
✓ Privacy - no external CA knows your infrastructure
✓ Cost - no ongoing certificate fees

✗ Trust chain - must distribute CA certificate to all services
✗ Revocation - no built-in revocation mechanism (must implement CRL)

WHY AUTO-ROTATION (90 DAYS)?

✓ Security - limits exposure time if certificate is compromised
✓ Compliance - meets industry best practices (NIST SP 800-57)
✓ Automation - reduces operational overhead
✓ Early warning - rotation 15 days before expiration

WHY PER-CLIENT CERTIFICATES?

✓ Isolation - compromised client doesn't affect others
✓ Revocation - can revoke individual clients
✓ Audit - clear attribution of actions
✓ Scalability - supports multiple vault instances
✓ Zero-trust - follows security best practices

WHY mTLS + EPHEMERAL TOKENS?

✓ Defense in depth - multiple security layers
✓ Transport security - mTLS prevents MITM attacks
✓ Application security - tokens provide fine-grained authorization
✓ Compatibility - works alongside existing token auth
✓ Migration - can deploy mTLS without breaking existing clients

================================================================================
ALTERNATIVES CONSIDERED
================================================================================

Alternative 1: External PKI (Let's Encrypt / commercial CA)
✗ Requires external dependencies
✗ Cannot work offline
✗ ACME protocol complexity for internal services
✗ Certificate fees (commercial CA)
✗ Privacy concerns (CA learns about infrastructure)

Alternative 2: Shared certificate (one cert for all clients)
✗ Compromised client exposes all vaults
✗ No individual client isolation
✗ Cannot revoke individual clients
✗ Violates zero-trust principles

Alternative 3: No mTLS (ephemeral tokens only)
✗ No transport layer security
✗ Vulnerable to MITM attacks on network level
✗ No cryptographic identity verification
✗ Lower security posture

Alternative 4: Manual certificate rotation
✗ High operational overhead
✗ Risk of missed rotations
✗ Service disruption during manual updates
✗ Human error risk

Alternative 5: Longer certificate lifetime (365+ days)
✗ Increased exposure time
✗ Violates NIST recommendations
✗ Larger blast radius if compromised
✗ Less frequent rotation = less practice

================================================================================
SECURITY ANALYSIS
================================================================================

THREATS MITIGATED:

1. Man-in-the-Middle (MITM) attacks
   - Mitigation: mTLS provides cryptographic identity verification
   - Both client and server verify each other's certificates

2. Eavesdropping on UDS (if filesystem compromised)
   - Mitigation: TLS encryption protects data in transit
   - Strong cipher suites with forward secrecy

3. Impersonation attacks
   - Mitigation: CA-based certificate validation
   - Per-client certificates limit blast radius

4. Certificate expiration
   - Mitigation: Automatic rotation 15 days before expiration
   - Health checks monitor certificate age

5. Unauthorized access
   - Mitigation: Dual-layer security (mTLS + ephemeral tokens)
   - Both layers must pass for request to succeed

6. Key compromise
   - Mitigation: Per-client certificates isolate impact
   - Automatic rotation limits exposure time

SECURITY TRADE-OFFS:

✓ Enhanced security: mTLS adds strong cryptographic protection
✗ Increased complexity: Certificate management adds operational overhead
✓ Defense in depth: Dual-layer security is more robust
✗ Performance overhead: TLS adds latency to gRPC calls (minimal for UDS)
